# 跨子系统图谱查询

## 本实例的查询规模

本 skill 是个人工作台定位，单个实例通常只包含 1-3 个子系统。大多数查询在单一子系统内完成。跨子系统查询相对少见，但当使用者负责多个相关子系统时仍然需要。

## 核心原则

1. **关系定义在发起方** — `from` 所在子系统的 `relations/` 目录持有该关系
2. **按需加载关系文件** — 只加载当前推理需要的关系类型
3. **实体 ID 是连接点** — 跨子系统关系通过完整实体 ID（`{type}:{subsystem}:{name}`）连接

## 典型查询模式

### 模式 1: 单子系统 RCA（最常见）

告警→依赖链追踪，通常在本子系统内完成：

```
读 {subsystem}/relations/depends_on.yaml + runs_on.yaml
沿 from→to 反向遍历找根因
检查 critical 和 confidence 标签
```

### 模式 2: 跨子系统依赖追踪

当根因可能在另一个子系统时：

```
Step 1: 从告警实体出发，读本子系统 depends_on.yaml
Step 2: 发现依赖指向另一子系统（如 app:order:x → mq:shared:y）
Step 3: 切换到目标子系统，读其 depends_on.yaml 继续追踪
Step 4: 直到定位根因实体
```

### 模式 3: 爆炸半径评估

给定要变更的实体，找所有受影响方：

```
Step 1: 扫描本实例所有子系统的 depends_on.yaml
Step 2: 找 to={变更实体} 的所有关系
Step 3: 读相关子系统的 supports.yaml 查业务影响
```

## 查询效率建议

1. **只加载需要的关系文件** — RCA 只需 depends_on + runs_on
2. **优先本子系统** — 大多数问题根因在同一子系统内
3. **沿 critical + confirmed 路径优先** — 高置信度的关键依赖最可能是真实问题
4. **深度上限 5 层** — 超过时暂停汇报当前发现

## 注意

本 skill 实例只能看到使用者维护的子系统。如果依赖链延伸到其他人维护的子系统，需要协调对方查询其实例，或等待未来 CMDB/K8s MCP 可用后通过 MCP 查询。
